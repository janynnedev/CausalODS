Próximo passo: alterar o e2e_runner.py

O próximo passo é automatizar exatamente o que você acabou de executar manualmente.

O runner deverá:

1. receber o cenário;
2. determinar qual serviço será o alvo;
3. configurar order-service e payment-service separadamente;
4. recriar apenas os serviços necessários;
5. aguardar os serviços ficarem disponíveis;
6. enviar o pedido;
7. medir request_duration_ms;
8. localizar o trace correspondente;
9. consultar o RCA;
10. validar o serviço previsto;
11. validar reliability e incidente;
12. restaurar os dois serviços para mode=none.

Cenário	Alvo	Modo	HTTP esperado	Causa raiz
healthy	nenhum	none	200	nenhuma
payment_failure	payment	error	5xx	payment-service
payment_latency	payment	latency	200	payment-service
order_failure	order	error	503	order-service
order_latency	order	latency	200	order-service

Antes de alterar o runner, preserve a versão atual:

cp \
  experiments/e2e_runner.py \
  experiments/e2e_runner.before-order-scenarios.py

Confira:

ls -lh \
  experiments/e2e_runner*.py
  
  
3. Campanha final

Para uma comparação atualizada entre v1 e v2:

5 cenários
× 50 repetições
× 2 versões
= 500 execuções

A campanha precisa ser executada separadamente para cada versão:

python3 experiments/e2e_runner.py \
  --scenario all \
  --repeat 50 \
  --expected-runtime-version v1

Depois:

python3 experiments/e2e_runner.py \
  --scenario all \
  --repeat 50 \
  --expected-runtime-version v2

Não recomendo iniciar essas 500 execuções manualmente antes de criar o orquestrador, porque erros de versão, diretório ou restauração podem invalidar a comparação.  
  
  
./experiments/run_e2e_campaign.sh \
  start \
  --campaign-id final-v1-v2-50
